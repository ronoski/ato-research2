A compositional state-machine theory of authentication failure

Provenance, not Reachability

The worst account-takeover bugs are not unintended paths in a login automaton. They are broken answers to a different question — what justifies the privileges the system is holding right now? — and that question is invisible to any model of a single session.

Abstract

Account-takeover (ATO) and authentication-bypass vulnerabilities are conventionally hunted as reachability faults: model the login protocol as an automaton and search for an unintended path to an "authenticated-as-victim" state. This paper argues the framing is structurally wrong for the most damaging modern ATOs. We reframe the target property from state reachability to trust-provenance integrity: every privileged binding a system holds — a session bound to an account, an identifier marked verified, a capability granted to a session — must trace to a proof event demonstrating control of exactly the resource the binding privileges, by the same principal, within a freshness window. A vulnerability is a reachable configuration holding a binding whose provenance is empty (gap), forged (forgery), or upgraded from a weaker fact (laundering).

We show provenance is a property of the composition of many principals' lifecycle automata over a shared identity store, and give a Composition-Blindness argument: subsystems that each satisfy the classical single-session reachability property can compose into a system that violates provenance integrity — so the dominant ATO class is unmodelable per-session by construction. We provide a relational formalization, a taxonomy filing known attacks (pre-account-hijacking, OAuth link confusion, reset-token survival, remember-me bypass) under the three failures, and a two-track method — a relational Alloy model and provenance-annotated automata learning — that turns the theory into counterexamples.

§1The reframe

Ask a security engineer to model authentication and you get a login automaton: anon → password → mfa → authenticated, plus a scatter of error edges. Hunting takeover then means searching for an unintended path to the authenticated state — a skipped check, a step reached out of order. This is the reachability view, and protocol state fuzzing turned it into a discipline: enumerate the inputs, learn the machine the server actually implements, and diff it against the intended one.

The reachability view is correct, and it is not enough. The takeovers that mattered most in recent years — pre-account-hijacking, OAuth account-linking confusion, recovery flows that trust the wrong inbox — are not unintended paths in anyone's login automaton. Each principal's machine is well-behaved in isolation. The bug lives in what they share.

The move this paper makes is to stop asking which states are reachable and start asking what justifies the privileges the system is currently holding. That property has a name in access control — provenance — that has never been made the organising invariant for account-lifecycle security. Doing so is the contribution.

§2A relational framework

Fix four finite sets. Principals P — the actors, including one or more attackers. Identifiers I — emails, phone numbers, usernames, OAuth subjects, WebAuthn credential IDs. Channels C — the media through which control is demonstrated: knowledge (a password), an email inbox, an SMS endpoint, a TOTP/WebAuthn authenticator, a federated IdP. Accounts A — rows in the identity store. The system's state is not one session; it is the whole store plus every live session and every outstanding token, indexed across all of P.

Trust is not a boolean. It is a small lattice, climbed one proof at a time.

With those pieces the core objects are three short definitions and one invariant.

Definition 1 · Privileged binding

A privileged binding B is any fact the system relies on to grant access: a session → account binding, an identifier → account "verified" binding, or a capability → session grant. Each binding empowers a principal to act, and privileges a specific resource.

Definition 2 · Proof event

A proof event P = ⟨p, r, c, t⟩ records that principal p demonstrated control of resource r over channel c at time t. Entering a password proves knowledge of a secret; clicking an emailed link proves control of an inbox; completing an IdP flow proves control of a federated account.

Definition 3 · Provenance & justification

prov(B) is the set of proof events the system actually used to justify binding B. The predicate justifies(prov(B), B) holds iff those proof events demonstrate control of exactly the resource B privileges, by the principal B empowers, within B's freshness window.

Invariant TPI · Trust-Provenance Integrity

Every privileged binding the system holds, in every reachable configuration, is justified by its own provenance:

∀ reachable G . ∀ B ∈ privileged(G) . justifies( prov(B), B )

A vulnerability is a reachable configuration G holding some binding B with ¬justifies(prov(B), B). Every entry in the §5 taxonomy is one shape of that negation.

§3Three ways provenance fails

Negating justifies is not open-ended. A binding's provenance can be wrong in exactly three ways: it can be missing, it can point at the wrong resource, or it can be upgraded from something weaker. These are the whole failure surface.

§4Composition-Blindness

Here is the load-bearing claim, and the reason single-session modeling cannot be patched into sufficiency. It is one observation about the difference between a level and its provenance.

Theorem 1 · Composition-Blindness (informal)

Let subsystems S₁…Sₙ — password, OAuth-link, recovery, MFA, email-change — each be a single-principal automaton satisfying the classical property "no unintended path reaches full." Let ⊗Sᵢ be their composition over a shared identity store, with the natural interface: a proof event emitted in Sᵢ's alphabet raises a trust level that Sⱼ's guard reads. Then ⊗Sᵢ can hold a reachable configuration violating TPI — even though no Sᵢ violates its local property.

Proof sketch. Each Sᵢ's guard is a predicate over a local trust level. A level is a scalar. Provenance is a pair — (who proved, which resource). Composition transports the scalar across the interface but not the pair: Sᵢ can raise identifier e to verified on behalf of principal V (the victim's IdP proof), while Sⱼ's guard reads only "e is verified" and binds it into a session whose principal is A — because the store row is shared and only the level crossed. The violating configuration is reachable in ⊗Sᵢ yet is a path in no Sᵢ: it requires two principals' timelines to interleave through one shared row, an interleaving no single-principal model contains. Hence any method whose unit of analysis is one session is blind to it by construction, not by omission. ∎

The corollary is uncomfortable and useful: a system can be assembled entirely from subsystems that each pass their own state-machine audit and still be trivially takeover-able. "Secure by parts" is not a weaker version of secure; for this bug class it is unrelated to it. That is the precise sense in which levels compose and provenance does not.

§5A taxonomy by failure

The framework earns its keep if disparate, separately-named attacks turn out to be one invariant broken three ways. They do. The right-hand column also states where each bug lives — and therefore what kind of model can see it.

Attack classFailureWhat is laundered / missingWhere it lives
Pre-account-hijacking Laundering attacker-seeded row (claimed, prov=A) upgraded to verified, prov=V composition · 2 principals, shared row
OAuth "link to existing account" via unverified IdP email Laundering an IdP email claim never verified, treated as a verified binding cross-channel · IdP → store
Reset token survives email / password change Laundering proof pinned to the old inbox consumed after the row was rebound provenance-breaking transition · temporal
"Remember this device" survives password reset / step-up removal Laundering pre-MFA session proof carried past the MFA guard provenance-breaking transition · temporal
Host-header / cache-poisoned reset link Forgery reset proof delivered to an attacker-controlled resource single-session (proof → wrong r)
SAML / OIDC audience or subject confusion Forgery an assertion for resource R accepted as proof for R′ cross-channel
IDOR on user-id in a state-changing endpoint Gap a privileged action with empty provenance single-session (still caught classically)
JWT alg / signature bypass Out of scope — broken cryptographic integrity, not broken provenance — crypto layer, not the state machine

Two things to read off the table. First, every laundering row lives in composition or in time — precisely the region Theorem 1 says single-session models cannot reach. Second, the framework has an honest edge: JWT signature bugs are real ATOs and are not provenance failures. A theory that explained everything would explain nothing; this one draws its own boundary.

§6Worked exploit: pre-hijacking as laundering

Read the canonical pre-account-hijack through the lens. The attacker never breaks a login. They arrange for a legitimate future proof — the victim's own — to land on a row they already control, and let the system launder it.

§7From theory to counterexamples

A theory of this class is only worth the tooling it enables. Two tracks operationalize it — one for when you have the source, one for when you have only the endpoint. Both begin by naming the alphabet and tagging every symbol with the provenance triple, because that tag is the thing the classical models throw away.

§8Falsifiable predictions

A thesis that cannot be wrong is not a thesis. Three predictions make this one refutable, and each names what would sink it.

  • P1

    There exist deployed auth systems with zero findings under single-session / protocol-state fuzzing that yield ATO under two-principal proof-event replay (§7, track B).Refuted if: composition never adds a finding that a single-session pass could not have reached.

  • P2

    Enforcing the TPI clause set — provenance-tag every row, and re-justify (revoke-and-rebind) on every identity-mutating transition — closes the entire laundering column without per-attack patches.Refuted if: a laundering ATO survives full TPI enforcement — then the invariant is incomplete and must be refined.

  • P3

    Forgery-class bugs are detectable single-session; laundering-class strictly requires ≥2 principals or a temporal gap between proof and use.Refuted if: a laundering bug is caught by a faithful single-principal model — then the §5 partition is wrong.

§9Novelty, prior art, and limits

The ingredients are not new, and pretending otherwise would be the fastest way to be dismissed. Confused-deputy (Hardy) named the shape of trusting the wrong actor; provenance is a settled idea in access control; protocol state fuzzing (de Ruiter & Poll, USENIX 2015) is the black-box template; the web-infrastructure OAuth models (Fett–Küsters–Schmitz) supply formal SSO analysis; and the pre-hijacking catalog (Sudhodanan & Paverd, 2022) is the empirical spark.

The contribution is the synthesis and one argument. Specifically: (a) naming trust-provenance integrity as the single safety property under which these separately-named ATOs are one bug broken three ways; (b) the Composition-Blindness argument (§4) that isolates why the dominant class evades single-session modeling — levels compose, provenance does not; and (c) a relational method that checks that invariant rather than reachability. Prior work found the phenomenon; this supplies the invariant it violates and the reason it is systematically missed.

The limits are real and worth stating plainly. The model is only as good as the state variables chosen — abstract away the one the bug lives in and TPI will "prove" a safety it does not have, so in black-box use it is a hypothesis generator, never a safety certificate. Not all ATO is provenance: signature bugs, memory corruption, SSRF-to-metadata, and social engineering sit outside the boundary the §5 table draws on purpose. The black-box track infers behavior, not intent, and inherits every blind spot of automata learning. And the temporal side — freshness windows, TOCTOU races between proof and use — is sketched here as ordering, not yet formalized as timed automata. Each of those is the next paper.
